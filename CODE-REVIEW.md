# Code Review — tuner (2026-09-29)

Обзорное ревью всего кода: `pitch-core` (DSP-ядро), `audio-input` (native-захват),
`egui` (десктопный клиент), `web` (Vue 3 / WASM / TS-fallback), инфраструктура
кодогенерации и CI. Фокус — баги, риски, качество; архитектурные документы
(`ARCHITECTURE.md`, `TOP-500-backlog.md` и т.д.) сами по себе предметом ревью
не были — сверялся с ними только в той мере, в какой код им соответствует.

## Общая оценка

Качество кода заметно выше среднего. Это не «стартап-спагетти», а проект с
инженерной дисциплиной: единственный источник правды для данных и констант с
кодогенерацией и `--check` в CI, realtime-гигиена в аудио-колбэках, осмысленные
численные решения (f64-аккумуляция, параболическая интерполяция, One-Euro с
задокументированным тюнингом), обширные тесты с регрессионными комментариями и
дифференциальный quality-гейтом на реальном корпусе. `unsafe` в Rust нет;
`unwrap`/`panic!` — только в тестах; в TS нет ни одного `as any`/`@ts-ignore`;
`JSON.parse` из storage — под try/catch с нормализацией.

Существенных багов в DSP-логике (YIN/MPM/арбитраж/октавы/трекинг) я не нашёл:
реализации соответствуют каноническим алгоритмам, краевые случаи (пустой буфер,
вырожденные окна, NaN/∞ в конфигах, отрицательные частоты) везде закрыты.
Найденные проблемы — в основном в инфраструктуре вокруг ядра.

## Находки

### M1. Таймаут воркера навсегда роняет WASM-путь на TS-fallback
**Файл:** `web/src/composables/usePitchLoop.ts` (константа `PITCH_WORKER_TIMEOUT_MS`,
функции `requestPitchDetection`, `disablePitchWorker`)

Очередь запросов к pitch-воркеру имеет таймаут 1.5 с. Если ответ не пришёл за
это время, вызывается `disablePitchWorker()`, который ставит
`workerDisabled = true` — и это **навсегда** (до пересоздания компонента):
`ensurePitchWorker()` больше никогда не создаст воркер.

Проблема в том, что в бюджет 1.5 с попадает и **холодный старт WASM**:
первый `process` в воркере делает `import()` модуля + `wasm.init()` (fetch +
компиляция). На медленной сети или слабом устройстве один-единственный простой
>1.5 с на старте — и вся сессия до перезагрузки страницы работает на
TS-fallback. Дополнительный риск: fallback (`analyzePitchFrame`) в этой ветке
считает YIN прямо **на главном потоке** (O(τ·N) на 8192 сэмплах × 30 Гц) —
то есть в момент, когда воркер «не справляется», UI получает ещё и jank.

Рекомендации:
- разделить бюджеты: длинный таймаут на первый ответ (холодная загрузка),
  короткий — на steady-state;
- после таймаута не банить воркер пожизненно, а перезапускать с бэкоффом
  (например, 2–3 попытки, затем fallback);
- main-thread fallback увести в тот же воркер (TS-путь там уже есть и
  покрыт тестами — `PitchCoreAdapter.fallbackFrame`) либо в отдельный
  дешёвый воркер.

### M2. Два теста жёстко завязаны на окружение и дают ложные падения
**Файлы:** `web/tests/rustDomainParity.test.ts`, `web/tests/spectrogramBenchmarkProvenance.test.ts`
**Статус: исправлено 2026-09-29** — добавлены skip-гварды (`describe.skipIf`/`it.skipIf`)
с комментариями; проверка фикстуры вынесена в отдельный always-on тест. В CI
гейты остаются блокирующими: `build-web.yml` ставит Rust и делает
`fetch-depth: 0`.

Оба воспроизводимо падают вне «полного» окружения CI:

1. `rustDomainParity.test.ts` выполняет `spawnSync('cargo', …)` без проверки
   наличия тулинга — на машине без Rust весь файл падает с `ENOENT`.
2. `spectrogramBenchmarkProvenance.test.ts` делает
   `git show 57e71dc…:web/src/components/Spectrogram.vue` — требует
   **конкретный исторический коммит** в локальной истории. На зеркалах,
   squashed-чекаутах (в том числе в этой рабочей копии), shallow-клонах
   `git show` падает с `exists on disk, but not in '<sha>'`.

В полном CI (cargo + полная история) оба зелёные, поэтому это не баг
продукта, а баг разработческого опыта: любой форк/контрибьютор получает
красный `npm test` без объяснения. Рекомендация — `skip`-гварды с явным
сообщением («requires cargo», «requires full git history»), как уже сделано
для 3-skipped тестов.

### L1. TS-fallback трекер: bias медианы на чётной длине истории
**Файл:** `web/src/utils/pitchTracking.ts` (`update`, inlier-ветка)
**Статус: исправлено 2026-09-29** — медиана усредняет два центральных значения
(как в Rust), добавлен регрессионный тест `averages the two central history
values on even length` в `web/tests/pitchTracking.test.ts` (проверено: на старом
коде тест падает).

При длине истории 2 (`Math.floor(2/2) = 1`) берётся **верхний** из двух
центральных элементов — смещение вверх ровно после каждого commit, когда
история только что сброшена. Rust-двойник этот баг явно исправил
(`pitch-core/src/tracking.rs::history_median` усредняет два центральных
значения + регрессионный тест `history_median_averages_the_two_central_values_on_even_length`).
Fallback-путь остался со старым поведением. Патч тривиальный — повторить
rust-формулу.

### L2. TS-fallback сглаживание — legacy stepped-alpha вместо One-Euro
**Файл:** `web/src/utils/pitchTracking.ts` (alpha 0.20/0.35/0.55)

Заявлено как осознанно «degraded fallback» (и покрыто фикстурами), но при
реальном откате с WASM пользователь увидит другую динамику стрелки: ядро
использует адаптивный One-Euro (`pitch-core/src/one_euro.rs`), fallback —
ступенчатый EMA. Держать в бэклоге: либо портировать One-Euro (он простой и
без аллокаций), либо задокументировать расхождение в UI-диагностике
(флаг `detectorBackend` уже есть).

### L3. Декодер WAV отклоняет файлы с битыми trailing-чанками
**Файл:** `web/src/audio/wav.ts` (`decodeWav`, цикл по чанкам)

Любой чанк, чей `chunkLength` выходит за конец файла, обрушивает весь импорт
(`throw new Error('Invalid WAV: truncated … chunk')`). Для `fmt `/`data` это
правильно, но многие рекордеры пишут кривые `LIST`/`JUNK`/`fact`-хвосты —
валидное аудио будет отвергнуто целиком. Рекомендация: `fmt ` и `data`
валидировать строго (сейчас так и есть), metadata-чанки с некорректной
длиной — пропускать/обрезать до конца файла.

### L4. `diagnostics` computed использует `isListening` до его объявления
**Файл:** `web/src/composables/useTunerSession.ts`

`const diagnostics = computed(...)` читает `isListening.value`, тогда как
`const isListening = computed(...)` объявлен ниже по коду. Сейчас это работает
только потому, что тело computed ленивое и выполняется после setup. При
рефакторе (например, обращение во время setup) — TDZ-ошибка. Достаточно
поменять порядок объявлений.

### L5. `audio-input`: отравленный мьютекс колбэка молча гасит кадры
**Файл:** `audio-input/src/lib.rs` (`process_frames`)

Если пользовательский `on_frame` когда-либо паникует, мьютекс остаётся
poisoned и `if let Ok(mut on_frame) = on_frame.lock()` просто перестаёт
вызывать обработчик — поток продолжает жить, кадры теряются молча до
остановки сессии. В supervised-режиме это стоило бы хотя бы логировать
(или брать `unwrap_or_else(|p| p.into_inner())`). Крайний случай, но
неочевидный при диагностике «микрофон работает, тюнер мёртв».

## Мелочи (nits)

- **`fuse()` смешивает несопоставимые шкалы уверенности** (`pitch-core/src/dsp/candidates.rs`):
  в комментариях детально объяснено, что YIN `1−CMNDF` и MPM `NSDF-peak` — разные
  шкалы (C82), для error-prediction их пересчитывают через калибровочные кривые,
  а в `fuse()` confidence просто усредняется как есть. На работу не влияет
  (итоговая уверенность пересобирается в `ConfidenceEstimator`), но
  не консистентно с философией модуля.
- **A4 ограничен 420–460 Гц** и в web (`normalizeSettings`), и в egui (слайдер):
  при заявленных темпераментах/транспозиции это режет baroque 415 Гц. Если
  ограничение осознанное — стоит комментария.
- **egui без l10n** диагностических подсказок — в коде уже есть
  `TODO(presentation)`; для десктопной версии, которая позиционируется как
  полностью оффлайн и двуязычная по духу web-версии, это единственная
  незакрытая UX-дыра в заголовке окна.
- **`play_random_string`** (`egui/src/app.rs`) использует `SystemTime` nanos
  `% len` для «случайности» — работает, но не равномерно; для кнопки «сыграть
  случайную струну» приемлемо.
- **YIN/MPM сложность O(τ·N) в f64** — на native/WASM в рабочем потоке это
  нормально (около 10M FLOP на lane), но это тот же код, что крутится на
  главном потоке в main-thread-fallback (см. M1) — очередной довод в пользу
  переноса fallback из UI-потока.

## Сильные стороны (отдельно, это редкость)

1. **Единственный источник правды + кодогенерация.** `registry/music-registry.json`,
   `scripts/generate-*.mjs`, generated-модули в Rust и TS, `codegen:check` в
   каждом сценарии сборки/тестов. Гейт, который реально не даёт языкам
   разойтись — плюс `rustDomainParity` как второй эшелон.
2. **Realtime-гигиена `audio-input`.** Колбэк cpal — только downmix в
   переиспользуемые чанки из фиксированного пула и relaxed-счётчик; DSP и
   доставка кадров — на выделенном потоке; supervised recovery — отдельная
   тестируемая state machine с типизированными кодами событий.
3. **Численная аккуратность ядра.** f64-аккумуляция CMNDF/NSDF, параболическая
   интерполяция с clamp, NaN-санитизация конфигов, reset biquad-состояния при
   restart (найдено restart-soak'ом — видно по комментариям), clamp-ы на границах
   UI (`normalized_ratio`).
4. **Тесты как evidence, а не для галочки.** Лицензированный WAV-корпус с
   SNR/reverb-сеткой, дифференциальный гейт против `quality-baseline.json`,
   restart soak с проверкой бounded-историй, replay-парити native↔WASM↔egui,
   регрессионные тесты с описанием «что именно сломалось раньше».
5. **Supply-chain/безопасность.** Actions закреплены по SHA с комментариями,
   first-party actions, `persist-credentials: false`, лимит 64 МБ на WAV,
   строгая нормализация всех персистимых настроек (включая импорт профилей),
   отсутствие `unsafe`, отсутствие `unwrap` в production-путях.
6. **Архитектура вокруг lifecycle.** `SessionLifecycle` с сериализацией
   операций, ревизиями и корректной утечкой-остановкой «протухшего» старта;
   discriminated union портов ввода с capability-гейтами; worker-протокол с
   семантикой `resolved|unresolved` вместо проверки имени бэкенда.
