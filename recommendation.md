# Recommendations & Top 50 Problems

**Current state audit (fresh grounded pass, 2026-07-01)**

This is the canonical **top 50 things done poorly or incorrectly** in the guitar tuner codebase right now. It replaces the previous 183-item `R#` extract with a freshly re-grounded, independently re-verified list.

This file also holds a second, broader section further down — **["Full Backlog: 509 Problems, Improvements & Design Suggestions (By Piece)"](#full-backlog-509-problems-improvements--design-suggestions-by-piece)** — organized by a SOLID/DRY module decomposition into 32 small "pieces" so the codebase can be worked through incrementally, one piece at a time, instead of as one flat list. It also includes concrete improvement ideas and a real product/visual-design critique, not just bugs. See its own methodology note where it starts.

## Methodology

Six parallel audits each read the live source directly (not prior docs): web composables/state, web domain/DSP/visualization, `pitch-core` Rust, Tauri desktop native audio, egui native, and tests/CI/build/PWA/docs-accuracy. That produced 85 raw findings, which were deduplicated and ranked into 70 candidates, then **each candidate was independently re-verified against the current file content by a separate skeptic pass** (69/70 confirmed or corrected; 1 refuted as already fixed). The 50 highest-severity/highest-impact confirmed findings are below.

**Why a full re-audit instead of trusting the existing docs:** the prior audit trail — this file's old 183 `R#` items and [TOP-200-current.md](TOP-200-current.md)'s 187 `C#` items — had drifted from the live code in verifiable ways. For example, they described `pitch-core/src/lib.rs` as a ~654-668 line monolith with YIN/MPM at specific line ranges inside it, but the crate had already been split into `domain.rs`, `dsp.rs`, `engine.rs`, `frames.rs`, `signal.rs`, `smoother.rs`, and `lib.rs` is now ~191 lines of mostly re-exports and tests. They also listed "egui `play_random_string` drops its output stream via `out.take()`, so the tone never plays" and "`AudioContext` never `resume()`d" as open P0s — both were already fixed in the code (`egui/src/main.rs` has a comment noting the old `out.take()` bug was removed; `web/src/composables/useAudioInput.ts` already calls `audioContext.resume()` and listens for `track.onended`). This pass is grounded directly in the current source.

**Not refreshed in this pass:** [TOP-200-current.md](TOP-200-current.md), [TOP-500-backlog.md](TOP-500-backlog.md), [RECOMMENDATIONS.md](RECOMMENDATIONS.md) and [PLAN.md](PLAN.md) still use the old `R#`/`C#`/`M#` numbering and, in places, the same stale evidence this pass corrected. Treat their specific line-number citations as historical until they get their own re-grounding pass; their high-level direction (layering, ports, realtime safety, single-source domain) is still directionally correct and consistent with the findings below.

Synced documents:
- [ARCHITECTURE.md](ARCHITECTURE.md) describes the target architecture and links back here.
- [README.md](README.md) summarizes the same debt for users and contributors.

Priority key: **P0** correctness / realtime safety / a shipped claim that's actually false, **P1** high-impact architecture, coupling, duplication or missing-test risk, **P2** quality / performance / DX gap with lower but real impact, **P3** polish.

## Top 50 Problems (ranked, most severe first)

### P0 — correctness, realtime safety, false claims

1. **Three independently-maintained YIN pitch detectors (web TS, Rust `pitch-core`, Tauri desktop) have diverged, and the web/desktop copies are missing bugfixes the Rust reference already has.** `web/src/utils/pitch.ts:69-151`; `pitch-core/src/dsp.rs:1-139`; `desktop/src-tauri/src/native_audio.rs:287-383`.
   - Evidence: `pitch-core/src/dsp.rs` documents in-code that computing the YIN difference function only from `min_tau` (as `pitch.ts` still does) skewed the cumulative-mean normalization, and adds an adaptive threshold and DC-offset subtraction neither the TS implementation nor desktop's hand-rolled `detect_pitch_yin` (fixed 0.12 threshold, no MPM fallback) received. Desktop already imports `pitch_core` (`frequency_to_note`, `normalize_level`) but reimplements YIN from scratch instead of calling the crate's detector — the actual public entry point it could call is `pitch_core::detect_pitch_native`/`detect_pitch` (the `_internal` fns are `pub(crate)`-only).
   - Impact: the browser tuner (all non-Tauri users) and the Tauri desktop tuner both run YIN variants missing fixes the Rust side's own comments say were needed to avoid octave/semitone errors and DC-bias inaccuracy. `rustDomainParity.test.ts` only checks pure note/tuning math, never DSP output, so nothing catches the divergence.
   - Fix: port the corrected running-sum start, adaptive threshold and DC-offset subtraction into `pitch.ts`; delete `native_audio.rs`'s duplicate YIN and call `pitch_core::detect_pitch_native` instead; add a cross-language parity test over shared synthetic buffers.

2. **Both native desktop apps (egui and Tauri) run heap-allocating pitch detection, FFT and mutex locks directly inside the realtime cpal audio callback.** `egui/src/main.rs:518-554`; `desktop/src-tauri/src/native_audio.rs:195-212`.
   - Evidence: egui's `build_input_stream` closure calls `engine_for_cb.lock()` (contended with the UI thread at lines 235/251/442) then `eng.process()` inline, which allocates fresh `diff`/`yin`/`nsdf`/`spectrum` `Vec`s every call with no throttling. Tauri's callback does `buffer.extend`/`drain` (reallocation), locks `shared_range` (contended with the command thread), allocates two fresh 2048-element `Vec<f32>` per call, then synchronously calls `app.emit()`.
   - Impact: allocating/locking inside a realtime audio callback is a textbook realtime-safety violation — allocator stalls or lock contention can miss the callback deadline and produce audible clicks/dropouts, especially on strict-latency backends (WASAPI exclusive, small CoreAudio buffers).
   - Fix: in both apps, have the callback only copy samples into a lock-free ring buffer/channel; move YIN/FFT/IPC emit to a dedicated worker thread that owns the engine and reuses preallocated buffers.

3. **Rust `pitch-core`'s detection frequency range is hardcoded to 30-400Hz (guitar-only), silently breaking detection for every non-guitar tuning it exposes.** `pitch-core/src/dsp.rs:1-2,31-32,134,196`.
   - Evidence: `GUITAR_MIN_FREQ`/`GUITAR_MAX_FREQ` are private, non-configurable consts bounding both the tau search range and the final frequency gate in `detect_pitch_yin_internal`/`detect_pitch_mpm_internal`; nothing on `detect_pitch` or `TunerEngine::process` overrides them.
   - Impact: `pitch_core::get_tunings()` (used directly by egui) includes Mandolin/Violin/Banjo/12-string/Ukulele tunings whose upper strings exceed 400Hz (violin E5≈659Hz); selecting these in egui's picker means the detector returns `None` for those strings every time — total, silent detection failure, not degraded accuracy.
   - Fix: add a configurable min/max Hz range to `EngineConfig`/`TunerEngine` and thread it through the detectors, mirroring what `pitch.ts` and `native_audio.rs` already support independently.

4. **egui's tuning editor updates the displayed frequency and reference tone but never syncs the live `TunerEngine`, so cents/note detection silently uses the stale pre-edit frequency.** `egui/src/main.rs:234-257`.
   - Evidence: the "edit current tuning" slider block mutates `self.tunings[self.t_idx].strings[i].frequency` directly and only calls `e.reset()` on change — never `e.set_tuning(...)`. `TunerEngine` holds its own owned `Tuning` clone used by `find_closest_string`/`get_cents`, so it keeps the old frequency until the ComboBox selection is redone.
   - Impact: a user who nudges a custom string frequency sees the slider and reference tone update, but the cents-off/in-tune needle keeps computing against the old frequency — a silent correctness bug in exactly the feature meant to support custom tunings.
   - Fix: in the slider's `.changed()` handler, call `e.set_tuning(tuning.clone())` instead of only `e.reset()`.

5. **Release workflow tags and publishes a GitHub Release even when the Tauri and/or egui desktop builds fail, with no marker indicating the release is incomplete.** `.github/workflows/release.yml:50-121`.
   - Evidence: the release job runs `if: always()` with desktop artifacts only downloaded when their build `result == 'success'`, but "Create tag"/"Create GitHub Release" run unconditionally whenever `steps.version.outputs.skip != 'true'`, regardless of `build-tauri`/`build-egui` outcome.
   - Impact: if a Windows/macOS Tauri or egui leg fails, a real, publicly-tagged release still goes out containing only a subset of platform artifacts with nothing distinguishing it from a complete one — users on the missing platform get no installer and no explanation.
   - Fix: gate the tag/release steps on `needs.build-tauri.result == 'success' && needs.build-egui.result == 'success'`, or explicitly mark the release draft/partial when a platform build failed.

6. **App manifest and `index.html` claim the PWA "works offline" but no service worker exists anywhere in the web source tree.** `web/public/manifest.webmanifest:4`; `web/index.html:8`.
   - Evidence: the manifest description reads "Works offline"; `index.html`'s meta description says "Works offline as PWA." A repo-wide search under `web/` for `serviceWorker`/`sw.js`/`workbox`/`VitePWA` finds zero matches; `main.ts` never registers one.
   - Impact: a user who installs the PWA and opens it offline gets a blank page instead of a working tuner — a shipped claim that is simply false.
   - Fix: add a real service worker (e.g. `vite-plugin-pwa` with a precache strategy) before shipping the claim, or remove/soften the "works offline" wording until it exists.

7. **Rapid/repeated mic-toggle calls re-enter `useAudioInput.start()` during the pending `getUserMedia` await, leaking `MediaStream`s and `AudioContext`s.** `web/src/composables/useAudioInput.ts:41-88,123-128`; `web/src/App.vue:43-59`.
   - Evidence: `start()` only guards with `if (isListening.value) return`, but `isListening.value` isn't set until *after* `await getUserMedia(...)` resolves. `App.vue`'s key handler has no `e.repeat` guard and the mic button has no disabled-while-pending state, so holding Space or double-clicking re-enters `start()` mid-flight; `setInputDevice` has the same unguarded-overlap problem.
   - Impact: two concurrent `getUserMedia` calls create two streams/contexts; the second overwrites the module-scoped variables, so the first stream's tracks and `AudioContext` are never stopped and leak until the tab closes.
   - Fix: add a synchronous in-flight guard (set before the first `await`, cleared in `finally`) in `start()`; ignore `e.repeat` keydowns in `App.vue`; have `setInputDevice` wait for any in-flight start to settle.

8. **`test_yin_440hz` explicitly accepts an octave-down (220Hz) detection as passing, masking the exact class of error the surrounding code was patched to fix.** `pitch-core/src/lib.rs:39-55`.
   - Evidence: `assert!((f - 440.0).abs() < 10.0 || (f - 220.0).abs() < 10.0, ...)` — a pure 440Hz sine detected a full octave flat is treated as a pass.
   - Impact: this is the most canonical test case (pure A4 sine, no harmonics) and it explicitly tolerates a full-octave error; a future regression reintroducing octave-down bias would not be caught by the simplest possible input, giving false confidence in the detector.
   - Fix: tighten the assertion to require the fundamental within a few Hz of 440.0; add a separate, explicitly-labeled test if intentional subharmonic tolerance is ever needed elsewhere.

### P1 — architecture, coupling, duplication, missing-test risk

9. **Desktop's duplicated YIN/RMS logic has zero unit tests, unlike `pitch-core`'s tested guitar-note/octave-guard suite.** `desktop/src-tauri/src/native_audio.rs` — no `#[test]`/`#[cfg(test)]` anywhere in the crate; `compute_rms` (lines 283-285) and an inlined second RMS copy inside `detect_pitch_yin` (line 299) duplicate `pitch_core::compute_rms_volume` with copy-pasted gate constants.
   - Impact/Fix: the Tauri build's actual pitch-detection path is hand-copied and untested — the historical bug class fixed in `pitch-core` could exist right now on desktop with zero signal. Route through `pitch_core` (see #1); short-term, port the guitar-note/DC-offset tests over and reuse `compute_rms_volume`.

10. **No test exercises YIN/MPM/autocorrelation against each other or the Rust reference; only pure domain/note math has cross-language parity coverage.** `web/tests/rustDomainParity.test.ts`; `web/src/utils/core.test.ts:96-144`.
    - Impact/Fix: real Rust-side DSP bugfixes have no mechanism to reveal the web/desktop paths still have the old buggy behavior (compounds #1). Extend the parity fixture to compare detector *output* (frequency + confidence), not just domain math.

11. **Every web build compiles a wasm `pitch-core` module that is never imported or used anywhere in the app.** `web/package.json` (`build:wasm` in `dev`/`build`/`build:tauri`); zero `wasm` references anywhere under `web/src`.
    - Impact/Fix: every dev-server start and production build pays the cost and fragility of a wasm-pack build (which silently swallows failure) that is dead weight — the actual browser detector is the drifted TS reimplementation. Either wire the wasm build in as the real detector, or delete the `build:wasm` step, the `wasm` feature and the `wasm-bindgen` exports.

12. **`test_power_chord` discards its own assertion target and cannot fail even if power-chord detection is completely broken.** `pitch-core/src/lib.rs:69-85` — `let _ = is_likely_power_chord_native(&buf, sr, freq);`; the test only asserts `detect_pitch_native` returned `Some(_)`, never that the signal was classified as a power chord.
    - Impact/Fix: this feature is silently untested and could regress to always-false with the suite still green (see also #39, hardcoded false on desktop). Assert `true` for the synthetic fundamental+fifth mix and add a negative-case pure-sine test.

13. **cpal stream error callback (Tauri desktop) only `eprintln!`s, with no frontend notification, leaving the UI silently frozen on mid-session device disconnect.** `desktop/src-tauri/src/native_audio.rs:212`.
    - Impact/Fix: unplugging a USB mic mid-session leaves `isListening` true and the frame simply stops updating with no error shown, no reconnect. Emit a `native-audio-error` event from the error callback via a cloned `AppHandle` and surface it through the existing frontend error ref.

14. **Input and output cpal streams on egui hardcode f32 sample buffers without checking the device's actual `SampleFormat`, unlike the sibling Tauri implementation.** `egui/src/main.rs:508-518,590-599,643-652` vs `desktop/src-tauri/src/native_audio.rs:138-176` (which matches all `SampleFormat` variants).
    - Impact/Fix: on any device whose default format isn't F32 (common on some Windows WASAPI/ALSA configs), the stream build call fails and mic/reference-tone silently fail to start with just an `eprintln`. Match on `sample_format()` and dispatch to typed builders, mirroring the Tauri side.

15. **egui's one Mutex lock on the per-frame UI hot path is `unwrap()`'d unguarded, so a single audio-thread panic poisons the lock and crashes the whole app.** `egui/src/main.rs:126` — `self.st.lock().unwrap().clone()`; every other lock site in the file uses `if let Ok(...)`.
    - Impact/Fix: an audio-callback panic (e.g. an edge-case index bug inside DSP) poisons the mutex, and the very next `update()` call panics on `.unwrap()`, taking down the app instead of degrading gracefully. Match on the lock result and fall back on poison, matching the pattern used elsewhere in the file.

16. **egui's DSP pipeline runs unthrottled inside the input callback, unlike the Tauri sibling which gates processing to ~30fps.** `egui/src/main.rs:518-554` vs `desktop/src-tauri/src/native_audio.rs:190-210` (tracks `last_emit: Instant`, skips unless ≥33ms elapsed).
    - Impact/Fix: on devices with small callback buffers, the 2048-sample window fills and re-runs full YIN+FFT far more often than the UI needs, burning audio-thread CPU and increasing the odds of a missed deadline. Add the same elapsed-time gate used on the Tauri side.

17. **Tauri desktop builds are shipped unsigned on macOS and Windows with no CI secrets configured for signing or notarization.** `desktop/src-tauri/tauri.conf.json:45-64` (`signingIdentity: null`, `certificateThumbprint: null`); no `TAURI_SIGNING`/`APPLE_*`/`CSC_*` secrets anywhere in `build-tauri.yml`.
    - Impact/Fix: every published `.dmg`/`.app`/`.exe` triggers Gatekeeper "unidentified developer" and SmartScreen warnings — a real adoption blocker for a consumer app requesting microphone access. Add signing/notarization secrets, or explicitly document the unsigned state and how to bypass OS warnings.

18. **Web-audio path always reports binary confidence (0 or 1) while the native/Tauri path reports genuine graded YIN confidence, making confidence-driven UI inconsistent across backends.** `web/src/composables/useTunerSession.ts:134-146` (`confidence: freq == null ? 0 : 1`) vs `pitch-core/src/dsp.rs:95-96` (real `1.0 - yin[v]`, passed through by the native adapter).
    - Impact/Fix: the same on-screen confidence indicator means fundamentally different things per backend. Have `detectPitch`/`detectPitchYIN` in `pitch.ts` return a real graded value and thread it through instead of hardcoding 0/1.

19. **`useTuner.detectionFrame` unconditionally discards the native backend's own cents/note/target/inTune fields and recomputes them from `freq` alone.** `web/src/composables/useTuner.ts:43-52`.
    - Impact/Fix: only `freq`/`level`/`rms`/`confidence`/`isPower` from native are ever used; native's own cents/note/target/inTune computation is dead work serialized over IPC and thrown away every frame (compounds #4, where native's target can be stale anyway). Stop sending the dead fields, or use them directly and add a test asserting the two paths agree.

20. **`Spectrogram.vue` repaints its entire 150×128 history grid with a per-cell string-template `fillStyle` every animation frame instead of scrolling and drawing only the new column.** `web/src/components/Spectrogram.vue:59-103`.
    - Impact/Fix: up to ~19,200 `fillRect` calls and string allocations per draw at ~60fps is enough canvas work to visibly drop frame rate or contend with the audio pipeline. Shift the existing image by one column via an offscreen canvas/`drawImage` and paint only the newest column; precompute a color lookup instead of a fresh string per cell.

21. **`Spectrum.vue` allocates a new `CanvasGradient` for every bar on every draw frame.** `web/src/components/Spectrum.vue:46-85` — up to 160 `createLinearGradient` calls/frame at ~60fps for a gradient shape that only varies in height.
    - Impact/Fix: unnecessary GC pressure and per-frame CPU on the thread also handling analyser polling and Vue reactivity. Precompute a single reusable gradient sized to canvas height.

22. **The core state-management composables (`useTuner`, `useTuningState`, `useSettings`) and most other composables have zero test coverage.** `web/tests/` has exactly 3 files; grepping for `useTuner`/`useSettings`/`useTuningState`/`useMetronome`/`useEarTraining`/`useCentsHistory`/`useReferenceTone`/`useCanvasRenderer`/`useHiDpiCanvas`/`useVisualizationFrames`/`useNativeAudioInput`/`App.vue` across those tests returns nothing — 12 of 15 composables untested.
    - Impact/Fix: the 487-line `useTuningState.ts` and 302-line `useTuner.ts` orchestrator (backend switching, streak math, the `detectionFrame` override from #19) can regress silently. Add tests using the fake-timer harness already established in `tunerSession.test.ts`; prioritize `useSettings` (data loss) and `useMetronome` (timing) first.

23. **Rust `pitch-core`'s module files (`domain.rs`, `dsp.rs`, `engine.rs`, `smoother.rs`, `signal.rs`, `frames.rs`) have no unit tests of their own; all coverage lives in `lib.rs`'s single integration-style test module.** Grepping each module file for `#[test]` returns zero matches in every one; all 9 tests live in `lib.rs`.
    - Impact/Fix: `domain.rs` (note/cents math, tunings, closest-string) and `smoother.rs` (used every audio frame — see #46's stale-history bug) have no tests scoped to their own module boundary. Move/add `#[cfg(test)]` blocks into each module directly.

24. **`CentsHistory.vue` is a fully-built, dead canvas component duplicating `CentsHistoryGraph.vue` with no live callers.** `web/src/components/CentsHistory.vue` — no `<CentsHistory ` usage anywhere; `App.vue` renders `CentsHistoryGraph.vue` instead, with a different data contract.
    - Impact/Fix: two implementations with different contracts and no signal about which is current; any fix to `CentsHistory.vue` has zero effect on the shipped app. Delete one.

25. **egui and Tauri desktop crates have zero unit tests and are never linted (no clippy/fmt); only compiled via release build in CI.** `.github/workflows/build-egui.yml:57-62`; `build-tauri.yml:78-83` — only `cargo build --release`/`tauri build`, no `test`/`clippy`/`fmt` step across 803 and 383 lines of native-audio glue.
    - Impact/Fix: regressions in the two largest hand-written native-audio surfaces can only be caught by a successful compile, not correctness or lint (including realtime-unsafe allocation patterns, see #2). Add `cargo clippy --workspace -- -D warnings` and `cargo test --workspace` jobs.

26. **Rust `domain.rs` has no temperament/sweetening data at all, so the shared "domain" layer isn't actually shared for a core tuning feature.** `pitch-core/src/domain.rs` — equal-tempered only; no Rust equivalent of `web/src/utils/notes.ts`'s 7 `TEMPERAMENTS` or 13 `SWEETENING_PROFILES`.
    - Impact/Fix: egui/native cannot offer the same historical-temperament or sweetened-tuning features without a second, independently-drifting reimplementation. Port temperament/sweetening into `domain.rs` if it's meant to be cross-platform, or document it as web-only by design.

27. **`NativeAudioFrame` (Tauri) hand-duplicates `pitch-core`'s `DetectionFrame` shape with an extra legacy `frequency` alias field the frontend must special-case.** `desktop/src-tauri/src/native_audio.rs:21-42,269-271`; `web/src/composables/useNativeAudioInput.ts:5-7,121` (`payload.freq ?? payload.frequency ?? null`).
    - Impact/Fix: any future field added to `pitch_core::DetectionFrame` (already happened once, `spectrum`) won't automatically appear on desktop. Derive the serialization directly from `DetectionFrame` and drop the alias once the frontend only reads `freq`.

28. **No `PitchDetector` trait/abstraction; YIN and MPM are ad-hoc free functions chained with a hardcoded `if-let` fallback.** `pitch-core/src/dsp.rs:203-229` — `detect_pitch` tries YIN, falls back to MPM, then `None`, with no way for a caller to select/compose/test a strategy without editing the function body.
    - Impact/Fix: adding a third strategy requires editing the hardcoded chain; blocks unit-testing the fallback boundary in isolation. Introduce a small `PitchDetector` trait with a `CompositeDetector` encoding the current order.

29. **All three canvas visualizers go completely blank on the native (Tauri) audio backend, and separately render an empty canvas during synthetic-audio sessions, with no substitute or indication either way.** `web/src/App.vue:105-120`; `web/src/composables/useTuner.ts:32-37`.
    - Evidence: the visualizer `v-if`s gate only on `!usingNativeAudio`; the frame-capture condition also requires `!usingSyntheticAudio`, but the visualizer `v-if`s don't check that, so a `?fixture=` synthetic session shows blank canvases while detection is actively working.
    - Impact/Fix: Tauri desktop users (a first-class target) lose all visualizers with no explanation; either surface waveform/spectrum data from native audio, or hide the toggles when `usingNativeAudio`/`usingSyntheticAudio` is true.

30. **`Fretboard.vue` and `PerStringCents.vue` are fully-built components with zero callers anywhere in the app.** No `<Fretboard`/`<PerStringCents` usage anywhere outside their own files; not imported by `App.vue`.
    - Impact/Fix: two complete, seemingly-finished features (fretboard target visualizer, per-string status strip) are invisible to users. Wire them in or delete them.

31. **`set_range` (both web and Tauri desktop) silently discards a valid user-supplied frequency range and resets to defaults with no error surfaced when a narrow-ratio check fails.** `desktop/src-tauri/src/native_audio.rs:240-248`; `web/src/utils/pitch.ts:58-62` (identical bug, duplicated).
    - Impact/Fix: a user picking a legitimately narrow instrument range that trips the 1.2x ratio check gets silently reset to the full default with no feedback. Return an error/validation result instead of silently substituting defaults, and consolidate the validation into one place.

32. **`desktop/src-tauri` has no input device selection; it always opens the OS default input device despite the web app supporting device picking.** `desktop/src-tauri/src/native_audio.rs:59-62,132-134` — no device-id command parameter anywhere.
    - Impact/Fix: a desktop user with multiple mics/interfaces has no way to pick which one native audio uses, with no UI indication that device choice is unavailable. Add a device-id parameter to `start_native_audio` and wire it to the existing device-picker UI.

33. **`useMetronome` and `useReferenceTone` never `resume()` their `AudioContext`, unlike `useAudioInput`, so clicks/reference tone can be silently inaudible on autoplay-restricted browsers.** `web/src/composables/useMetronome.ts:21-26`; `useReferenceTone.ts:12-17` vs `useAudioInput.ts:66-73` (which does check/resume).
    - Impact/Fix: on Safari/iOS, starting the metronome or reference tone before the mic can produce complete silence with no error. Factor the resume-on-suspended logic into a shared helper used by all three call sites.

34. **Sine-wave reference-tone synthesis is duplicated verbatim between `toggle_ref` and `play_random_string` in egui instead of a shared helper.** `egui/src/main.rs:575-622,625-678` — identical host/device/config lookup and an identical phase-accumulator sine closure, differing only in the frequency chosen.
    - Impact/Fix: any future fix (phase-wrap math, fade-in/out, amplitude) must be applied in two places and is easy to miss in one. Extract a shared `play_tone(&mut self, freq: f32)` helper.

35. **Restoring persisted A4 and tuning index from `eframe` storage on egui startup updates the UI fields but never re-syncs the `TunerEngine`.** `egui/src/main.rs:740-765` — `app.a4`/`app.t_idx` are set from storage, but `app.engine` still holds `TunerEngine::new(440.0)` with the default tuning; neither `set_a4` nor `set_tuning` is called in the restore block.
    - Impact/Fix: a user who set A4=442 and Drop D sees the UI reflect it after restart, but the engine keeps detecting against A4=440/Standard until manually re-touched — incorrect cents readings that silently contradict the displayed state. Call `set_a4`/`set_tuning` after restoring from storage, before returning the app.

36. **Playwright E2E suite is never executed by any CI workflow, so it can silently rot.** `web/e2e/synthetic-fixture.spec.ts` and `npm run test:e2e` exist, but grepping every workflow for `playwright`/`test:e2e` returns zero matches.
    - Impact/Fix: the synthetic mic-toggle → LISTENING → detected-note E2E flow can break without any CI signal. Add a CI job running `npm run test:e2e:install && npm run test:e2e`.

37. **`npm test`'s Rust/Web parity test shells out to `cargo run` with no Rust toolchain setup step in the workflow that runs it.** `.github/workflows/build-web.yml` sets up only Node; `rustDomainParity.test.ts` calls `cargo run -p pitch-core --example domain_snapshot` with no `dtolnay/rust-toolchain` step anywhere in that workflow.
    - Impact/Fix: the parity test passing today depends on the runner image happening to ship a compatible preinstalled Rust toolchain, not a declared dependency. Add an explicit Rust-toolchain step, matching `test-core.yml`.

38. **Release artifacts (web tarball, Tauri bundles, egui binaries) are published with no checksums, so integrity cannot be verified.** `.github/workflows/release.yml:110-121` — no `sha256sum`/checksum-file generation step anywhere before the release step.
    - Impact/Fix: combined with unsigned binaries (#17), users have no way to verify a download wasn't corrupted or tampered with. Generate a `SHA256SUMS.txt` before publishing.

### P2 — quality, performance, DX
